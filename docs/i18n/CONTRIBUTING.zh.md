# 贡献

## 一处改动属于哪里

这个仓库装着两样分量不同的东西。

[SPEC.md](../../SPEC.md) 描述了一份约定，其他工具应当不用读这里的一行代码就能实现它。对它的修改从一个 issue 开始，好让讨论发生在有人动手写补丁之前。一个悄悄放宽契约的 pull request，比一个直白说出自己想改什么的提议更难反驳。

`hooks/prove-it.sh` 是那份约定的一个实现，七十来行，针对它的 pull request 不需要什么繁文缛节。

如果你不确定自己动的是这两者中的哪一个，就开一个 issue 问一下。

## 门禁对你也一样适用

这个仓库有一个 `verify.sh`。在你提 pull request 之前先运行它：

```bash
./verify.sh
```

它会检查 shell 语法，运行 shellcheck，校验插件清单，强制执行下面的文本规则，把译文对齐到英文原文，并在一个临时目录里针对真实的 git 仓库运行门禁自己的测试套件。CI 会在 Linux 和 macOS 上运行同一个脚本，另外还有一个单独的任务，用来证明门禁仍然会拦下一个检查失败的仓库。

如果 `verify.sh` 失败了，去修原因。不要削弱 `verify.sh`。这是这个项目唯一不会合并的改动，理由正是这个项目存在的理由。

## 添加一项检查

当一项新检查本可以抓到一个真实的 bug 时，它是受欢迎的。故意弄坏点什么，看着你的检查发现它，然后把它修好，两者一起提交。一个没人看着它失败过的检查不算检查。

`scripts/` 下有两个脚本之所以存在，是因为它们的第一个版本在一个本已损坏的代码库上通过了。

## 翻译

`README.md` 和 `SPEC.md` 是正本，当译文与之分歧时，以 `SPEC.md` 的英文文本为准。`scripts/check_i18n.py` 把每一份译文对齐到它的原文：标题数量，标题到底有没有被翻译，重音符号有没有保住，代码块是否与英文逐字节一致，以及相对链接能不能解析到。

有两条规则容易把人绊倒。

绝不要用长破折号。不用 em dash、en dash、横杠或减号。在每一种语言里都只用普通的 ASCII 连字符，包括那些排版习惯上更偏好别的写法的语言，因为长破折号读起来像是机器写的文本。（这一段是把这些字符点名说出来，而不是把它们展示出来，因为 `scripts/check_no_long_dash.py` 也会读这个文件。）

始终保住重音符号。破折号规则只覆盖六个特定字符，并不是对非 ASCII 的封杀。`décidé` 仍然是 `décidé`，`è` 绝不会变成 `e'`。早期有一份译文因为过度套用第一条规则，把文件里每一个重音符号都抹掉了。

## 配方

配方是针对某一种技术栈的起点，而不是一个完工的 `verify.sh`。让它的运行时长保持在一分钟以内，优先选择产出证据的检查而不是产出意见的检查，并注明每项检查交付的是规范里四种证据中的哪一种。

## 提交

使用约定式提交（`feat:`、`fix:`、`docs:`、`chore:`）。在正文里说清楚改了什么以及为什么。如果你修了一个 bug，就说清楚你是怎么复现它的。

## 发布

维护者遵循 [RELEASE.md](../../RELEASE.md)。一次发布需要干净的本地 `./verify.sh`，
`main` 上绿色的 `verify`、`codeql` 和 `scorecard` workflow，以及 tag workflow
产出的 checksum 和 provenance attestation。不要从未验证的树发布。
