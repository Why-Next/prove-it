संस्करण 0.1 (draft)। एक repository घोषित करती है कि वह खुद को कैसे साबित करती है, और कोई agent तब तक completion का दावा नहीं कर सकता जब तक वह proof pass न हो जाए।

यह दस्तावेज़ ही contract है। `hooks/` में मौजूद script इसका एक implementation है, और जान-बूझकर एक छोटा। यह मान लेने से पहले कि tool यहाँ लिखी हर बात को लागू करता है, conformance levels पर खंड 5 पढ़ें।

## 1. समस्या

Coding agents अपनी turns इन जैसे वाक्यों के साथ समाप्त करते हैं:

- "Tests pass।" tests कभी चलाए ही नहीं गए।
- "Bug ठीक कर दिया।" bug कभी reproduce ही नहीं किया गया।
- "migration सुरक्षित है।" किसी scratch database पर कुछ भी लागू नहीं किया गया।

ये सामान्य अर्थ में झूठ नहीं हैं। एक agent यह अलग नहीं कर सकता कि उसने क्या किया बनाम उसका क्या इरादा था, इसलिए उसकी रिपोर्ट इरादे का वर्णन करती है। यह विफलता संरचनात्मक है, और prompting इसे नहीं हटाएगी। prompt तकनीक भी हर model पीढ़ी के साथ पुरानी पड़ जाती है, जबकि साक्ष्य की माँग model से एक परत ऊपर बैठती है और upgrade के बाद भी टिकी रहती है।

इसलिए "done" अब कोई ऐसी चीज़ नहीं रह जाता जिसे agent घोषित करता है, बल्कि एक ऐसा check बन जाता है जिसे उसे pass करना होता है।

## 2. कन्वेंशन

एक अनुरूप (conforming) repository की root पर एक executable file `verify.sh` होती है।

```
your-repo/
  verify.sh      <- executable, exit 0 means "this tree is provably fine"
```

contract:

| | |
|---|---|
| Location | repository की root |
| Mode | executable (`chmod +x`) |
| Invocation | repository की root पर CWD के साथ चलाएँ, कोई arguments नहीं |
| Exit `0` | verification pass हुआ |
| Exit non-`0` | verification fail हुआ; stdout और stderr बताते हैं क्यों |
| Output | मनुष्य के पढ़ने योग्य; आखिरी 20 लाइनें ही एक agent देखता है |
| Runtime | एक मिनट के भीतर; धीमे checks CI में होने चाहिए |
| Absent | कोई gate नहीं। अनुपस्थिति एक वैध state है, कोई विफलता नहीं |

`verify.sh` एक ही सवाल का जवाब देता है: यहाँ किए गए किसी बदलाव को वापस सौंपने लायक provably सुरक्षित मानने के लिए क्या सच होना चाहिए? हर repository इसका जवाब अलग तरह से देती है, इसीलिए यह convention file का नाम तय करता है, उसकी सामग्री का नहीं।

बाहर निकलने के लिए एक ही काम काफी है: `verify.sh` को delete कर दें, या उसे घटाकर `exit 0` कर दें। यह जान-बूझकर है। लोग ऐसे gate के इर्द-गिर्द रास्ता निकाल लेते हैं जिसे वे हटा नहीं सकते, और जिस gate के इर्द-गिर्द रास्ता निकाल लिया जाता है वह फिर भी सफलता की रिपोर्ट देता रहता है।

## 3. चार तरह के साक्ष्य

एक `verify.sh` को विश्वास के बजाय साक्ष्य के विरुद्ध जोर देना चाहिए। चार तरह के साक्ष्य वज़न रखते हैं। एक उपयोगी `verify.sh` इनमें से कम से कम एक को कवर करता है, और एक परिपक्व वाला अपने चलाए जाने वाले checks में चारों को कवर करता है।

**Command output.** एक command चली और check ने उसका exit code पढ़ा। "tests को pass होना चाहिए" नहीं, बल्कि test runner का अपना फैसला।

**Diff.** बदलाव वही है जो इरादा था और उससे ज़्यादा कुछ नहीं: कोई debug statement नहीं, कोई भटकी हुई file नहीं, कोई असंबद्ध formatting उथल-पुथल नहीं। `git diff --check` न्यूनतम स्तर है।

**Reproduction.** किसी bug fix के लिए, विफलता बदलाव से पहले देखी गई थी और उसके बाद मौजूद नहीं है। ऐसा fix जिसे कभी reproduce नहीं किया गया, बस एक अंदाज़ा है कि कौन-सी line गलत थी।

**Cross-check.** एक दूसरा, स्वतंत्र स्रोत सहमत होता है। कोई दूसरा model, कोई दूसरा tool, किसी test suite के विरुद्ध एक type checker। स्वतंत्रता ही इसे कुछ भी मूल्यवान बनाती है; एक ही धारणा साझा करने वाले दो checks code के बजाय उस धारणा की पुष्टि करते हैं।

ये चार श्रेणियाँ इसलिए हैं ताकि "मैंने इसे verify किया" को एक तरीका बताना पड़े। जो agent यह नहीं बता सकता कि उसके पास चारों में से कौन-सा साक्ष्य है, उसके पास उनमें से कोई भी नहीं है।

## 4. implementations को क्या करना चाहिए

इस convention का एक implementation एक gate है। अनुरूप होने के लिए उसे यह करना ही चाहिए:

1. agent की turn समाप्त हो पाने से पहले repository की root से `verify.sh` चलाए।
2. non-zero exit पर turn को block करे, और output सामने लाए।
3. जब gate चलने के समय `verify.sh` executable के रूप में मौजूद न हो और session
   की शुरुआत में भी executable के रूप में मौजूद न रहा हो, तो कुछ न करे।
4. जब session ने उस repository को न बदला हो तो कुछ न करे।
5. एक स्पष्ट, greppable bypass दे। एक चुपचाप bypass लोगों को gate पर अविश्वास
   करना सिखाता है; एक audited bypass इसे ईमानदार बनाए रखता है।
6. किसी विफल verification के बाद कभी किसी turn को चुपचाप समाप्त न करे। जो
   implementation किसी भी कारण से block करना बंद कर दे, उसे यह वहाँ कहना ही चाहिए
   जहाँ user देखेगा।

बिंदु 4 यह पूछता है कि क्या बदला, न कि किसने बदला। जो implementation इस आधार पर फैसला करता है कि agent ने कौन-से editing tools चलाए, वह `sed` से दोबारा लिखी गई file, `git apply` से लगाए गए patch, किसी code generator के output, और एक commit को चूक जाएगा। commit करना agent का सबसे साधारण काम है, और जो gate एक साफ working tree को साबित करने लायक कुछ न होना मानता है, वह ठीक उन्हीं turns को गुज़र जाने देगा जिन्हें पकड़ने के लिए वह मौजूद है। repository की तुलना उससे करें जैसी वह session शुरू होते समय दिखती थी।

बिंदु 3 दोनों क्षणों का उपयोग जानबूझकर करता है। मौजूदा stop इसलिए मायने रखता है
ताकि कोई installation command `verify.sh` बना सके और उसी session में repository
को arm कर सके। शुरुआती state इसलिए मायने रखती है ताकि session के बीच में delete
या `chmod -x` को gate को निहत्था करना माना जाए, ईमानदार opt-out नहीं।

बिंदु 6 इसलिए है क्योंकि जो gate हमेशा block कर सकता है वह session को अटका देता है, और हर host आखिरकार उसे हार मानने पर मजबूर कर देता है। यह ठीक है। जो ठीक नहीं है वह है ऐसे तरीके से हार मानना जो pass होने से अलग न पहचाना जा सके।

उसे `verify.sh` को संशोधित नहीं करना चाहिए, और उसे agent को बताना चाहिए कि gate को पार करने के लिए `verify.sh` को कमज़ोर करना कोई fix नहीं बल्कि एक उल्लंघन है। व्यवहार में यही सबसे संभावित failure mode है। जो agent किसी check को pass नहीं कर पाता, वह मौका मिलने पर उस check को ही संपादित कर देगा।

इसका सबसे भोंडा रूप check को हटा देना है। किसी implementation को दर्ज करना चाहिए कि session शुरू होते समय `verify.sh` मौजूद और executable था या नहीं, और ऐसी turn को अस्वीकार करना चाहिए जो उसे delete किए हुए या निहत्था किए हुए समाप्त होती है। sessions के बीच file को delete करना खंड 2 वाला opt-out है और उसे काम करते रहना चाहिए। जिस session को वह block करने वाली थी उसी के बीच में उसे delete करना कोई opt-out नहीं है, और इन दोनों के बीच का फर्क केवल उसी implementation को दिखता है जिसने पहले देखा था।

## 5. अनुरूपता के स्तर

इस बारे में सटीक रहें कि एक मशीन क्या लागू करती है और एक व्यक्ति क्या अभ्यास में लाता है। यह भेद convention के पीछे की महत्वाकांक्षा से ज़्यादा मायने रखता है।

**Level 1, gate.** `verify.sh` मौजूद है, और कोई चीज़ यांत्रिक रूप से किसी turn को उसके fail रहते समाप्त होने से मना कर देती है। `hooks/` में reference implementation इसे पूरी तरह लागू करता है, और यहीं से हर repository को शुरू करना चाहिए। "मना करने" का एक बजट होता है: यह turn को एक सीमित संख्या में बार वापस भेजता है और फिर एक चेतावनी के साथ हार मान लेता है, क्योंकि host किसी hook को हमेशा block नहीं करने देगा।

**Level 2, साक्ष्य.** `verify.sh` के भीतर के checks खंड 3 के चार तरह के साक्ष्यों को कवर करते हैं। कोई tool इसे लागू नहीं करता, यह वाला भी शामिल। gate यह verify करता है कि आपके `verify.sh` ने zero लौटाया। उस zero का कोई मतलब है या नहीं, यह आपके लिखे checks के बारे में एक दावा है, और केवल `exit 0` वाला `verify.sh` कुछ भी साबित किए बिना Level 1 तक पहुँच जाता है।

**Level 3, लेजर.** हर पकड़ी गई झूठी completion दर्ज होती है, ताकि failure modes किस्से के बजाय डेटा बन जाएँ। reference implementation इसे केवल तभी लिखता है जब स्पष्ट रूप से चालू किया गया हो।

Level 1 एक tool का गुण है। Level 2 एक टीम की आदतों का गुण है, और जो भी tool इसे देने का दावा करता है वह Level 1 दे रहा है और उम्मीद कर रहा है कि कोई source न पढ़े।

## 6. लेजर फॉर्मैट

चालू होने पर, हर पकड़ी गई झूठी completion प्रति line एक JSON object जोड़ती है:

```json
{
  "ts": "2026-07-09T04:12:33Z",
  "repo": "/home/you/src/api",
  "exit_code": 1,
  "claim": "All tests pass. Ready to merge.",
  "evidence_demanded": "verify.sh exit 0",
  "actual": ["FAIL src/auth.test.ts", "3 failed, 41 passed"]
}
```

`claim` में agent का अपना वह आखिरी संदेश होता है जो उसके रुकने की कोशिश करने से ठीक पहले का है। यह record में सबसे उपयोगी field है और सबसे संवेदनशील भी, क्योंकि इसमें बातचीत का कोई भी पाठ हो सकता है। एक implementation को ledger को प्रतिबंधात्मक permissions के साथ स्थानीय disk पर लिखना चाहिए और उसे कभी transmit नहीं करना चाहिए।

एक row तीन चीज़ें रखती है: क्या दावा किया गया, क्या माँगा गया, और क्या सच था।

## 7. गैर-लक्ष्य

यह convention आपको यह नहीं बताता कि क्या check करना है, आपकी CI नहीं चलाता, आपके code को अंक नहीं देता, और review की जगह नहीं लेता। यह एक ही सवाल का जवाब देता है, वह यह कि agent के चले जाने से पहले इस repository ने खुद को साबित किया या नहीं।
