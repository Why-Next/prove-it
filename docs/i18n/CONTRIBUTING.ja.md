# コントリビュート

## どこに変更を出すか

このリポジトリは、重みの異なる2つのものを抱えている。

[SPEC.md](../../SPEC.md) は、他のツールがこのコードを1行も読まずに実装できるはずの規約を記述している。それへの変更は issue として始まる。誰かがパッチを書く前に議論が行われるようにするためだ。契約をこっそり広げる pull request は、何を変えたいのかをはっきり述べる提案よりも、反論しにくい。

`hooks/prove-it.sh` はその規約の1つの実装で、70行そこそこだ。それに対する pull request に儀式は要らない。

2つのどちらに触れているのか分からないときは、issue を開いて尋ねてほしい。

## ゲートはあなたにも適用される

このリポジトリには `verify.sh` がある。pull request を開く前に、それを走らせること:

```bash
./verify.sh
```

これは、シェルの構文をチェックし、shellcheck を走らせ、プラグインのマニフェストを検証し、下記の文章ルールを強制し、翻訳を英語の原文に照らし合わせ、そしてゲート自身のテストスイートを、一時ディレクトリ内の本物の git リポジトリに対して走らせる。CI は同じスクリプトを Linux と macOS で走らせ、さらに、チェックが失敗するリポジトリをゲートがちゃんとブロックし続けることを証明する別ジョブを走らせる。

`verify.sh` が失敗したら、原因を直すこと。`verify.sh` を弱めてはならない。それは、このプロジェクトが存在する理由ゆえに、このプロジェクトがマージしない唯一の変更だ。

## チェックを追加する

新しいチェックは、それが本物のバグを捕まえていたはずのものなら歓迎する。わざと何かを壊し、あなたのチェックがそれに気づくのを見届け、それから直して、両方をコミットする。誰も失敗するのを見届けていないチェックは、チェックではない。

`scripts/` の下にある2つのスクリプトは、その最初のバージョンが、すでに壊れていたコードベースに対して通ってしまったから存在している。

## 翻訳

`README.md` と `SPEC.md` が正本であり、翻訳が食い違う場合は `SPEC.md` の英語テキストが優先される。`scripts/check_i18n.py` は、あらゆる翻訳を原文に照らし合わせる。見出しの数、見出しがそもそも翻訳されているか、アクセント記号が残っているか、コードブロックが英語とバイト単位で同一か、そして相対リンクが解決するか。

2つのルールが人をつまずかせる。

長いダッシュを決して使わないこと。em ダッシュも、en ダッシュも、水平バーも、マイナス記号もだめだ。どの言語でも、タイポグラフィがそれを好む言語であっても、素の ASCII ハイフンだけを使う。長いダッシュは機械が書いたテキストのように読めるからだ。(この段落は、`scripts/check_no_long_dash.py` がこのファイルも読むので、その文字を見せる代わりに名前で呼んでいる。)

アクセント記号は必ず残すこと。ダッシュのルールは6つの特定の文字を対象とするもので、非 ASCII の禁止ではない。`décidé` は `décidé` のままで、`è` は決して `e'` にはならない。ある初期の翻訳は、最初のルールを過剰に適用して、ファイル中のアクセント記号をすべて剥ぎ取ってしまった。

## レシピ

レシピは、完成した `verify.sh` ではなく、1つのスタックのための出発点だ。実行時間を1分以内に保ち、意見を生むチェックよりも証拠を生むチェックを選び、そして各チェックが仕様の4種類の証拠のどれを提供するかを書き添える。

## コミット

Conventional commits(`feat:`、`fix:`、`docs:`、`chore:`)。本文で、何がどう変わり、なぜ変わったかを述べる。バグを直したなら、どう再現したかを述べる。
