# 安全

## 这个软件在你的机器上做什么

`prove-it` 会运行一个位于你打开的仓库里的脚本。如果你打开一个你并不信任的仓库，而它的 `verify.sh` 是可执行的，那么你的智能体结束一个回合时就会执行那个文件。

这种行为是设计如此，而不是其中的缺陷，它带来的风险和你运行 `npm install` 或打开一个带 `Makefile` 的项目时已经接受的风险是同一种。在你让智能体去一个包含陌生 `verify.sh` 的仓库里工作之前，先读一读那个 `verify.sh`，就像你会去读一个陌生的 `postinstall` 脚本一样。

门禁只在以下情况才运行：本次会话改动过**同一个仓库**，而且它的根目录存在一个可执行的 `verify.sh`。克隆并阅读一个仓库从不会触发它，而改动一个仓库也从不会导致另一个仓库的 `verify.sh` 运行。

`prove-it doctor` 是个例外，而且是刻意的：是你叫它去运行门禁的，所以它会立即在你此刻所在的任何仓库里运行 `verify.sh`。不要在一个你还没读过它的 `verify.sh` 的仓库里运行它。

这一切都不是沙箱。这些钩子和它们的记账都以你的身份运行，代理的 shell 也一样，所以一个存心要击败门禁的代理，完全可以删掉状态目录，再解除 `verify.sh` 的武装。`prove-it` 是一道防护栏，防的是那种自信却出错的代理，也就是你手上的这一个。它不是一道抵御怀有敌意的代理的边界。一个怀有敌意的代理够不到的检查，必须运行在它够不到的地方，而那个地方就是 CI。

## 它往磁盘上写什么

一些小小的记账文件，都放在一个以 `0700` 权限创建的私有目录里：`$XDG_STATE_HOME/prove-it/`，或者当它未设置时是 `~/.local/state/prove-it/`。可以用 `PROVE_IT_STATE_DIR` 覆盖。它们记录的是：会话开始时树是什么样子、那一刻门禁有没有处于激活状态、一次会话写过哪些仓库、哪些树状态已经通过过，以及当前回合已经被顶回去多少次。每一个都存放一个校验和或一个小整数，绝不存放文件内容。不会往共享的 `/tmp` 里写任何东西，因为这些文件名是从仓库路径推导出来的，因此是可预测的，而一个位于所有人可写目录里的可预测名字就是一个符号链接攻击的目标。

会话标识符是从 hook 的 JSON 负载里来的，并且最终会成为上述某个文件名的一部分，所以在被使用之前，它会被削减到只剩字母、数字、短横线和下划线。一个负载并不是路径组成部分的可信来源。

可选的账本（`PROVE_IT_LEDGER=1`，**默认关闭**）会为每一次被抓到的虚假完成，向 `~/.prove-it/ledger.jsonl` 追加一行 JSON，该文件以 `0600` 权限创建，位于一个 `0700` 目录内。每一行包含：

- 智能体在试图停止之前的最后一条消息，截断到 300 个字符，取自你本地的对话记录，所以它可以包含你对话里的任何内容
- 仓库的绝对路径
- 退出码，以及你的 `verify.sh` 输出里点明某个失败的那几行
- 一个时间戳

把它当作对话数据来对待。这个项目里没有任何东西会回读它或把它发送到任何地方，但它仍然是一个普通文件，所以你的备份会复制它，任何对你主目录有读取权限的人都能打开它。

## 它发送什么

什么都不发送。在你机器上运行的软件不含遥测、不含网络调用、不含更新检查。你可以用一次 grep 来确认这一点：在 `hooks/` 和 `scripts/` 里搜索 `curl`、`wget`、`urllib`、`requests` 或 `socket`。

持续集成是唯一的例外，而它不是你运行的代码：GitHub Actions 工作流会从 `apt` 或 `brew` 安装 `shellcheck`，然后运行你在本地会运行的同一个 `verify.sh`。

## 报告漏洞

把细节和一份复现步骤发邮件到 **hello@whynext.app**。对于任何能让一个仓库突破上文所述边界的问题，请不要开一个公开的 issue。

预计几天之内会收到确认回复。这个项目由一个人维护，所以耐心会有帮助，一份复现步骤也会有帮助。一份我无法复现的报告，就是一份我无法修复的报告。
