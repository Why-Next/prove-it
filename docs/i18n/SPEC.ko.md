버전 0.1 (초안). 레포는 자기가 어떻게 스스로를 증명하는지 선언하고, 에이전트는 그 증명이 통과하기 전까지 완료를 주장할 수 없습니다.

이 문서가 계약입니다. `hooks/`에 있는 스크립트는 그 계약의 한 가지 구현이고, 일부러 작게 만든 것입니다. 이 도구가 여기 적힌 모든 걸 강제한다고 넘겨짚기 전에, 준수 레벨을 다루는 5절을 읽어보세요.

## 1. 문제

코딩 에이전트는 이런 문장으로 차례를 끝냅니다:

- "테스트 통과." 테스트는 한 번도 돌지 않았습니다.
- "버그 수정 완료." 버그는 한 번도 재현되지 않았습니다.
- "마이그레이션은 안전합니다." 임시 데이터베이스에 적용해본 것은 아무것도 없습니다.

이건 보통 의미의 거짓말이 아닙니다. 에이전트는 자기가 한 일을 하려던 일과 구분하지 못하므로, 그 보고는 의도를 서술합니다. 이 실패는 구조적이고, 프롬프트로는 없앨 수 없습니다. 프롬프트 기법은 모델 세대가 바뀔 때마다 낡아버리는 반면, 증거를 요구하는 것은 모델보다 한 층 위에 있어서 업그레이드에도 살아남습니다.

그래서 "완료"는 에이전트가 선언하는 것이 아니라 통과해야 하는 검사가 됩니다.

## 2. 컨벤션

이 컨벤션을 따르는 레포는 루트에 실행 가능한 `verify.sh` 파일을 둡니다.

```
your-repo/
  verify.sh      <- executable, exit 0 means "this tree is provably fine"
```

계약:

| | |
|---|---|
| 위치 | 레포 루트 |
| 모드 | 실행 가능 (`chmod +x`) |
| 호출 | CWD를 레포 루트에 두고 인자 없이 실행 |
| 종료 `0` | 검증 통과 |
| 종료 `0` 아님 | 검증 실패. stdout과 stderr가 이유를 설명한다 |
| 출력 | 사람이 읽을 수 있게. 마지막 20줄이 에이전트가 보는 것 |
| 실행 시간 | 1분 미만. 느린 검사는 CI에 둔다 |
| 없음 | 게이트 없음. 부재는 실패가 아니라 유효한 상태 |

`verify.sh`는 한 가지 질문에 답합니다. 여기서 만든 변경을 증명 가능하게 안전히 돌려주려면 무엇이 참이어야 하는가? 레포마다 답이 다르고, 그래서 이 컨벤션은 파일의 내용이 아니라 파일 이름을 정합니다.

빠져나가는 데는 한 가지 행동이면 됩니다. `verify.sh`를 삭제하거나 `exit 0`으로 줄이는 것. 이건 의도된 것입니다. 사람들은 없앨 수 없는 게이트는 돌아서 지나가고, 우회당한 게이트도 여전히 성공을 보고하니까요.

## 3. 네 종류의 증거

`verify.sh`는 믿음이 아니라 증거를 상대로 확인해야 합니다. 무게를 갖는 종류는 넷입니다. 쓸모 있는 `verify.sh`는 최소 하나를 다루고, 성숙한 `verify.sh`는 자기가 돌리는 검사들 전체에 걸쳐 넷을 모두 다룹니다.

**명령 출력.** 명령이 실행됐고 검사가 그 종료 코드를 읽었다. "테스트가 통과해야 한다"가 아니라 테스트 러너 자신의 판정.

**Diff.** 변경이 의도한 그것이고 그 이상은 없다. 디버그 문도 없고, 딸려 들어온 파일도 없고, 상관없는 포매팅 변경도 없다. `git diff --check`가 최소선입니다.

**재현.** 버그 수정이라면, 변경 전에는 실패가 관찰됐고 변경 후에는 사라졌다. 한 번도 재현되지 않은 수정은 어느 줄이 틀렸는지에 대한 추측일 뿐입니다.

**교차 확인.** 두 번째의 독립된 출처가 동의한다. 다른 모델, 다른 도구, 테스트 스위트를 상대로 한 타입 체커. 가치를 만드는 건 독립성입니다. 같은 가정을 공유하는 두 검사는 코드가 아니라 그 가정을 확인해줄 뿐입니다.

네 범주가 존재하는 이유는 "검증했다"는 말이 방법을 대라고 요구하기 위해서입니다. 네 종류의 증거 중 무엇을 쥐고 있는지 말하지 못하는 에이전트는 그중 아무것도 쥐고 있지 않은 겁니다.

## 4. 구현이 반드시 해야 하는 것

이 컨벤션의 구현은 게이트입니다. 준수하려면 다음을 해야 합니다:

1. 에이전트의 차례가 끝나기 전에 레포 루트에서 `verify.sh`를 실행한다.
2. 종료 코드가 0이 아니면 차례를 막고, 출력을 드러낸다.
3. 게이트가 실행되는 시점에 `verify.sh`가 실행 가능한 파일로 존재하지 않고,
   세션 시작 시점에도 실행 가능한 파일로 존재하지 않았으면 아무것도 하지 않는다.
4. 세션이 그 레포를 변경하지 않았으면 아무것도 하지 않는다.
5. 명시적이고 grep으로 찾을 수 있는 우회 수단을 제공한다. 조용한 우회는
   사람들에게 게이트를 불신하도록 가르치고, 기록이 남는 우회는 게이트를
   정직하게 유지한다.
6. 검증이 실패한 뒤에 차례를 조용히 끝내지 않는다. 어떤 이유로든 막기를
   멈추는 구현은, 사용자가 보게 될 곳에서 그렇다고 말해야 한다.

4번은 누가 바꿨는지가 아니라 무엇이 바뀌었는지를 묻습니다. 에이전트가 어떤 편집 도구를 호출했는지 지켜보는 방식으로 판단하는 구현은 `sed`로 다시 쓴 파일, `git apply`로 적용한 패치, 코드 생성기의 출력, 그리고 커밋을 놓칩니다. 커밋은 에이전트가 하는 가장 평범한 일이고, 깨끗한 워킹 트리를 증명할 것이 없다고 취급하는 게이트는 정작 자기가 잡으려고 존재하는 바로 그 차례들을 그냥 통과시킵니다. 레포를 세션이 시작될 때의 모습과 비교하세요.

3번은 두 시점을 일부러 함께 봅니다. 현재 stop 시점이 중요한 이유는 설치 명령이
`verify.sh`를 만들고 같은 세션 안에서 레포를 무장시킬 수 있어야 하기 때문입니다.
시작 상태가 중요한 이유는 세션 중간의 삭제나 `chmod -x`를 정직한 탈출이 아니라
게이트를 무장 해제한 것으로 다루기 위해서입니다.

6번이 있는 이유는 영원히 막을 수 있는 게이트가 세션을 멈춰 세우고, 모든 호스트는 결국 게이트를 양보하게 만들기 때문입니다. 그건 괜찮습니다. 괜찮지 않은 것은 통과와 구분되지 않는 방식으로 양보하는 것입니다.

구현은 `verify.sh`를 수정해서는 안 되고, 게이트를 통과하려고 `verify.sh`를 약화시키는 것은 수정이 아니라 위반이라고 에이전트에게 알려야 합니다. 이건 실제로 가장 일어나기 쉬운 실패 양상입니다. 검사를 통과하지 못하는 에이전트는 기회가 주어지면 그 검사를 편집합니다.

그 가장 조야한 형태는 검사를 아예 없애는 것입니다. 구현은 세션이 시작될 때 `verify.sh`가 존재하고 실행 가능했는지를 기록하고, 그 파일이 삭제되거나 무장 해제된 채로 끝나는 차례를 거부해야 합니다. 세션과 세션 사이에 파일을 삭제하는 것은 2절의 탈출구이고 계속 동작해야 합니다. 게이트가 막으려던 바로 그 세션 도중에 파일을 삭제하는 것은 탈출구가 아니며, 둘의 차이는 이전을 들여다본 구현에게만 보입니다.

더 미묘한 형태는 `verify.sh`를 실행 가능한 채로 두면서 그 안의 검사를 다시 쓰는 것입니다. 이건 게이트에 대한 정당한 작업까지 함께 거부하지 않고서는 거부할 수 없으므로, 구현은 세션이 시작될 때 `verify.sh`에 무엇이 담겨 있었는지를 기록하고, 세션 도중에 바뀐 `verify.sh`를 거쳐 차례가 통과하면 사용자가 보게 될 곳에서 그렇다고 말해야 합니다. 통과는 유지되지만, 침묵은 유지되지 않습니다.

## 5. 준수 레벨

기계가 강제하는 것과 사람이 실천하는 것을 정확히 구분하세요. 그 구분이 컨벤션에 담긴 야심보다 더 중요합니다.

**Level 1, 게이트.** `verify.sh`가 존재하고, 그것이 실패하는 동안에는 무언가가 기계적으로 차례를 끝내지 못하게 막는다. `hooks/`의 레퍼런스 구현은 이걸 온전히 강제하며, 모든 레포가 여기서 시작해야 합니다. "막는다"에는 한도가 있습니다. 정해진 횟수만큼 차례를 되돌려 보낸 뒤 경고와 함께 양보하는데, 호스트가 훅을 영원히 막게 두지 않기 때문입니다.

**Level 2, 증거.** `verify.sh` 안의 검사들이 3절의 네 종류 증거를 다룬다. 이건 어떤 도구도 강제하지 않으며, 이 도구도 마찬가지입니다. 게이트는 당신의 `verify.sh`가 0을 반환했는지 검증합니다. 그 0이 무언가를 의미하는지는 당신이 작성한 검사에 대한 주장이고, `exit 0`만 들어 있는 `verify.sh`는 아무것도 증명하지 못한 채 Level 1에 도달합니다.

**Level 3, 원장.** 잡아낸 거짓 완료가 모두 기록되어, 실패 양상이 일화가 아니라 데이터가 된다. 레퍼런스 구현은 명시적으로 켰을 때만 이걸 기록합니다.

Level 1은 도구의 속성입니다. Level 2는 팀의 습관의 속성이고, Level 2를 제공한다고 주장하는 도구는 사실 Level 1을 제공하면서 아무도 소스를 읽지 않기를 바라는 겁니다.

## 6. 원장 형식

켜져 있으면, 잡아낸 거짓 완료 하나하나가 한 줄에 JSON 객체 하나씩 덧붙습니다:

```json
{
  "ts": "2026-07-09T04:12:33Z",
  "repo": "/home/you/src/api",
  "exit_code": 1,
  "claim": "All tests pass. Ready to merge.",
  "evidence_demanded": "verify.sh exit 0",
  "actual": ["FAIL src/auth.test.ts", "3 failed, 41 passed"]
}
```

`claim`에는 에이전트가 멈추려 하기 직전 자기 마지막 메시지가 담깁니다. 기록에서 가장 쓸모 있는 필드이자 가장 민감한 필드인데, 어떤 대화 텍스트든 담길 수 있기 때문입니다. 구현은 원장을 제한적인 권한으로 로컬 디스크에 써야 하고, 절대 전송해서는 안 됩니다.

한 줄은 세 가지를 담습니다. 무엇을 주장했고, 무엇을 요구받았고, 무엇이 사실이었는지.

## 7. 목표가 아닌 것

이 컨벤션은 무엇을 검사할지 알려주지 않고, 당신의 CI를 돌리지 않고, 당신의 코드에 점수를 매기지 않고, 리뷰를 대체하지 않습니다. 이 컨벤션은 단 하나의 질문에 답합니다. 에이전트가 떠나기 전에 이 레포가 스스로를 증명했는가.
