バージョン 0.1(ドラフト)。リポジトリは自らをどう証明するかを宣言し、エージェントはその証明が通るまで完了を主張してはならない。

この文書が契約だ。`hooks/` にあるスクリプトはその1つの実装であり、意図的に小さくしてある。ここに書かれたすべてをツールが強制すると考える前に、適合レベルについての第5節を読んでほしい。

## 1. 問題

コーディングエージェントは、次のような文でターンを終える:

- 「テストは通る」。テストは一度も走らなかった。
- 「バグを修正した」。バグは一度も再現されなかった。
- 「このマイグレーションは安全だ」。スクラッチのデータベースには何も適用されなかった。

これらは、ふつうの意味での嘘ではない。エージェントは、自分がやったことと、やろうとしたことを区別できないので、その報告は意図のほうを述べる。この失敗は構造的なもので、プロンプトでは取り除けない。プロンプトの技法はモデルの世代ごとに古びていくが、証拠の要求はモデルの1つ上の層にあり、アップグレードを生き延びる。

こうして「完了」は、エージェントが宣言するものではなく、通過しなければならないチェックになる。

## 2. 規約

準拠するリポジトリは、ルートに実行可能なファイル `verify.sh` を持つ。

```
your-repo/
  verify.sh      <- executable, exit 0 means "this tree is provably fine"
```

契約:

| | |
|---|---|
| 場所 | リポジトリのルート |
| モード | 実行可能(`chmod +x`) |
| 呼び出し | CWD をリポジトリのルートにして、引数なしで実行する |
| 終了コード `0` | 検証は通過した |
| 終了コード `0` 以外 | 検証は失敗。標準出力と標準エラーが理由を説明する |
| 出力 | 人間が読める形式。エージェントが目にするのは最後の20行 |
| 実行時間 | 1分未満。遅いチェックは CI に属する |
| 存在しない場合 | ゲートは無い。不在は失敗ではなく、有効な状態だ |

`verify.sh` は1つの問いに答える。ここでの変更を、証明可能な形で安全に返せるようにするには、何が真でなければならないか? どのリポジトリもその答えは異なる。だからこの規約は、ファイルの中身ではなくファイル名を定める。

オプトアウトは1つの操作で済む。`verify.sh` を削除するか、`exit 0` だけに減らす。これは意図的だ。人は取り除けないゲートを回避し、回避されたゲートはそれでも成功を報告する。

## 3. 4種類の証拠

`verify.sh` は、思い込みではなく証拠に対して主張すべきだ。重みを持つ種類は4つある。役に立つ `verify.sh` は少なくとも1つをカバーし、成熟した `verify.sh` は走らせるチェック全体で4つすべてをカバーする。

**コマンド出力。** コマンドが走り、チェックがその終了コードを読んだ。「テストは通るはずだ」ではなく、テストランナー自身の判定だ。

**Diff。** 変更は意図されたものそのもので、それ以上ではない。デバッグ文も、はぐれたファイルも、無関係なフォーマットの変更もない。`git diff --check` が最低ラインだ。

**再現。** バグ修正では、失敗が変更の前には観測され、変更の後には消えている。一度も再現されていない修正は、どの行が間違っていたかについての当て推量だ。

**クロスチェック。** 2つ目の独立した情報源が同意する。別のモデル、別のツール、テストスイートに対する型チェッカー。独立性こそが価値を生む。前提を共有する2つのチェックは、コードではなくその前提を確かめているにすぎない。

この4つのカテゴリがあるのは、「検証した」が方法を名指しせざるを得なくなるためだ。4種類の証拠のどれを握っているか言えないエージェントは、そのどれも握っていない。

## 4. 実装が満たすべきこと

この規約の実装はゲートだ。準拠するには、次を満たさなければならない:

1. エージェントのターンが終わる前に、リポジトリのルートから `verify.sh` を実行する。
2. 終了コードがゼロ以外ならターンをブロックし、出力を表に出す。
3. ゲートが走る時点で `verify.sh` が実行可能ファイルとして存在せず、かつセッション開始時点でも実行可能ファイルとして存在していなかったときは何もしない。
4. セッションがそのリポジトリを変更していないときは何もしない。
5. 明示的で grep 可能なバイパスを提供する。無言のバイパスは、人にゲートを信用しないよう仕向ける。監査可能なバイパスは、ゲートを正直に保つ。
6. 検証が失敗したあと、ターンを無言で終えることは決してしない。どんな理由であれブロックをやめる実装は、ユーザーの目に入るところでそう告げなければならない。

第4点が問うのは何が変わったかであって、誰が変えたかではない。エージェントがどの編集ツールを呼んだかを見て判断する実装は、`sed` で書き換えられたファイル、`git apply` で当てられたパッチ、コードジェネレータの出力、そしてコミットを取りこぼす。コミットはエージェントがする最もありふれた操作であり、クリーンなワーキングツリーを証明すべきものが無いと見なすゲートは、まさに自らが捕まえるために存在するターンを素通りさせてしまう。リポジトリを、セッションが始まったときにどう見えたかと突き合わせること。

第3点は、この2つの時点を意図的に使っている。現在の stop が重要なのは、インストール用のコマンドが `verify.sh` を作り、同じセッション内でリポジトリを武装できるようにするためだ。開始時点の状態が重要なのは、セッション途中の削除や `chmod -x` を、正直なオプトアウトではなくゲートの武装解除として扱うためだ。

第6点があるのは、永遠にブロックできるゲートはセッションをハングさせ、どのホストもいずれそれに譲ることを強いるからだ。それは構わない。よくないのは、通過と見分けのつかないかたちで譲ることだ。

実装は `verify.sh` を変更してはならない。そして、ゲートを越えるために `verify.sh` を弱めることは、修正ではなく違反だとエージェントに伝えなければならない。これが実際にはもっとも起こりやすい失敗のかたちだ。チェックを通せないエージェントは、機会があればそのチェックを書き換える。

そのもっとも粗雑なかたちは、チェックを取り除くことだ。実装は、セッションが始まったときに `verify.sh` が存在し実行可能だったかどうかを記録し、それが削除されたり武装解除されたりした状態で終わるターンを拒むべきだ。セッションの合間にそのファイルを削除するのは第2節のオプトアウトであり、機能し続けなければならない。ゲートがまさにブロックしようとしていたセッションの途中でそれを削除するのは、オプトアウトではない。そして両者の違いは、事前に見ていた実装にしか見えない。

## 5. 適合レベル

機械が強制するものと、人が実践するものを、はっきり区別すること。この区別は、規約の背後にある野心よりも重要だ。

**Level 1、ゲート。** `verify.sh` が存在し、それが失敗している間はターンを終えさせないよう、何かが機械的に拒む。`hooks/` のリファレンス実装はこれを完全に強制する。そして、どのリポジトリもここから始めるべきだ。「拒む」には予算がある。ターンを有限の回数だけ差し戻し、それから警告とともに譲る。ホストはフックに永遠にはブロックさせないからだ。

**Level 2、証拠。** `verify.sh` の中のチェックが、第3節の4種類の証拠をカバーする。これを強制するツールは無い。このツールも含めてだ。ゲートは、あなたの `verify.sh` がゼロを返したことを検証する。そのゼロに意味があるかどうかは、あなたが書いたチェックについての主張であり、`exit 0` だけの `verify.sh` は、何も証明しないまま Level 1 に達する。

**Level 3、台帳。** 検出された偽の完了はすべて記録され、失敗のかたちが逸話ではなくデータになる。リファレンス実装は、明示的に有効化されたときだけこれを書く。

Level 1 はツールの性質だ。Level 2 はチームの習慣の性質であり、それを提供すると称するツールは、Level 1 を提供しつつ、誰もソースを読まないことを願っているにすぎない。

## 6. 台帳のフォーマット

有効化されている場合、検出された偽の完了ごとに、1行につき1つの JSON オブジェクトが追記される:

```json
{
  "ts": "2026-07-09T04:12:33Z",
  "repo": "/home/you/src/api",
  "exit_code": 1,
  "claim": "All tests pass. Ready to merge.",
  "evidence_demanded": "verify.sh exit 0",
  "actual": ["FAIL src/auth.test.ts", "3 failed, 41 passed"]
}
```

`claim` は、エージェントが停止しようとする前の、それ自身の最後のメッセージを保持する。記録のなかでもっとも有用なフィールドであり、同時にもっとも機微なフィールドでもある。会話のどんなテキストでも含みうるからだ。実装は、台帳を制限的なパーミッションでローカルディスクに書かなければならず、決して送信してはならない。

1行が3つのことを保持する。何が主張され、何が求められ、何が真だったか。

## 7. 非目標

この規約は、何をチェックすべきかを指図しないし、あなたの CI を走らせないし、あなたのコードを採点しないし、レビューの代わりにもならない。それはただ1つの問いに答える。エージェントが立ち去る前に、このリポジトリが自らを証明したかどうかだ。
