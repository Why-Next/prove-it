**Ваш агент не может завершить ход, пока репозиторий не докажет свою состоятельность.**

Кодовые агенты говорят "тесты проходят", ни разу их не запустив, и "исправлено",
ни разу не воспроизведя баг. И не со зла: агент не способен отличить то, что он
сделал, от того, что собирался сделать, поэтому он сообщает о намерении.

`prove-it` превращает *готово* в то, что агент обязан пройти, а не в то, что он
волен заявить. Положите `verify.sh` в корень репозитория. Когда агент пытается
остановиться, шлюз его запускает. Ненулевой код выхода - и ход не завершается.

```
agent: "All tests pass. Ready to merge."
       └─ tries to end turn
          └─ prove-it runs ./verify.sh
             └─ exit 1:  FAIL src/auth.test.ts  (3 failed, 41 passed)
                └─ turn blocked, agent keeps working

agent: "Actually, three tests were failing. Fixing."
```

Примерно в половине случаев агент, у которого потребовали доказательство,
отвечает "вы правы, это ещё не готово".

## Установка

Требуются `bash`, `git`, `python3`. Никаких пакетов, никакого демона, нигде не
надо регистрироваться. Клонируйте куда угодно:

```bash
git clone https://github.com/YOUR_ORG/prove-it ~/.local/share/prove-it
```

Подключите два хука к Claude Code, влив
[`hooks/settings.example.json`](../../hooks/settings.example.json) в свой
`.claude/settings.json` (для отдельного репозитория) или `~/.claude/settings.json`
(для всех).

Затем напишите единственный файл, который имеет значение:

```bash
cat > verify.sh <<'EOF'
#!/bin/bash
set -eu
cd "$(dirname "$0")"

npm test
npx tsc --noEmit
git diff --check

echo "verify.sh OK"
EOF
chmod +x verify.sh
```

Вот и вся настройка. В вашем репозитории пока нет `verify.sh`, так что, пока вы
его не напишете, шлюз вообще ничего не делает.

## Ваши первые пять минут

Начните с меньшего, чем вам кажется. `verify.sh`, который выполняет всего лишь
`git diff --check`, уже стоит иметь, и он пройдёт - а это научит вас, что шлюз
молчит, когда всё в порядке.

```bash
printf '#!/bin/bash\nset -eu\ncd "$(dirname "$0")"\ngit diff --check\n' > verify.sh
chmod +x verify.sh
./verify.sh                 # run it yourself first. Never ship a check you have not seen pass.
```

Теперь посмотрите, как он падает нарочно, чтобы вы убедились: шлюз настоящий:

```bash
sed -i.bak 's|git diff --check|git diff --check\nexit 1|' verify.sh && rm verify.sh.bak
```

Попросите агента отредактировать любой файл, а затем дайте ему закончить. Он
попытается завершить ход, шлюз запустит `verify.sh`, и ход будет заблокирован.
Уберите `exit 1` - и тот же агент проходит без препятствий.

Дальше добавляйте по одной настоящей проверке за раз: команду тестов, которую вы
на самом деле запускаете, потом проверку типов, потом гигиену диффа. Каждая
добавленная проверка - это фраза в вашем ответе на вопрос *что здесь значит
доказано*. Остановитесь, когда всё вместе занимает около минуты.

Ошибка, которой стоит избегать, - написать амбициозный `verify.sh` в первый же
день. Медленный или нестабильный шлюз обходят в течение недели, а обойдённый
шлюз хуже, чем никакого: он говорит вам, что проверка была, когда её не было.

## Как он решает, запускаться ли

Шлюз по умолчанию молчит. Он запускает `verify.sh`, только когда истинно
одновременно всё перечисленное:

- сессия действительно редактировала файлы (сессии только на чтение нечего доказывать)
- в корне репозитория есть исполняемый `verify.sh`
- в рабочем дереве есть незакоммиченные изменения
- именно это состояние дерева ещё не проходило проверку

Последнее означает, что прошедшее дерево проверяется один раз, а не при каждой
остановке. При провале агенту печатаются последние 20 строк вывода, чего обычно
достаточно, чтобы он исправил причину без подсказок.

Чтобы намеренно пройти шлюз: `PROVE_IT_SKIP=1`. Чтобы отключить его насовсем:
удалите `verify.sh`. И то, и другое - осознанное действие. Шлюз, который никто не
может убрать, - это шлюз, который обходят стороной.

## Возможность отказаться - это фича

Самый тяжёлый режим отказа - не нестабильная проверка. Это агент, который не
может пройти `verify.sh` и вместо этого тихо редактирует сам `verify.sh`.
Сообщение об ошибке шлюза прямо об этом говорит, а спецификация объявляет это
заявленным нарушением. Всё равно высматривайте это в своих диффах. Для того и
нужны доказательства через дифф.

## Соглашение о `verify.sh`

Скрипт в `hooks/` нарочно небольшой. Настоящий артефакт - это соглашение, которое
он реализует, записанное в **[SPEC.md](../../SPEC.md)**: репозиторий объявляет,
как он доказывает свою состоятельность, в известном месте, с известным контрактом,
и агент не вправе заявлять о завершении, пока это доказательство не пройдёт.

Прочтите спецификацию, чтобы узнать про четыре вида доказательств, которые
`verify.sh` должен утверждать, - вывод команды, дифф, воспроизведение, перекрёстная
проверка - и про уровни соответствия.

**Одна честная оговорка сразу.** Этот инструмент обеспечивает ровно одно: что
`verify.sh` вернул ноль до того, как ход завершился. А значит ли этот ноль
хоть что-нибудь, целиком зависит от проверок, которые вы написали. `verify.sh`,
содержащий лишь `exit 0`, пройдёт этот шлюз и не докажет ничего. Инструмент - это
Level 1. Доказательства - это Level 2, а Level 2 - это практика, а не фича.

## Рецепты

Отправные точки под каждый стек, в [`recipes/`](../../recipes/). Скопируйте одну в
`verify.sh` и вырежьте то, что не применимо. Держитесь в пределах минуты; медленные
проверки место в CI.

| | |
|---|---|
| [`node.sh`](../../recipes/node.sh) | tests, typecheck, lint, diff hygiene |
| [`python.sh`](../../recipes/python.sh) | pytest, ruff, mypy |
| [`go.sh`](../../recipes/go.sh) | go test, vet, gofmt check |
| [`flutter.sh`](../../recipes/flutter.sh) | analyze, test, format check |

Трудная часть внедрения - это никогда не подключение хука. Это ответ на вопрос
"что значит *доказано* в этом репозитории" - впервые.

## Журнал

Установите `PROVE_IT_LEDGER=1`, и каждое пойманное ложное завершение добавляет одну
строку в `~/.prove-it/ledger.jsonl`:

```json
{"ts":"2026-07-09T04:12:33Z","claim":"All tests pass. Ready to merge.",
 "evidence_demanded":"verify.sh exit 0","actual":["3 failed, 41 passed"]}
```

Что было заявлено, что было потребовано, что было правдой. Только локальный диск,
никогда не передаётся, выключено, пока вы это не включите. Через месяц вы перестаёте
гадать, как ваш агент терпит неудачу, и начинаете это читать.

## Этот репозиторий шлюзует сам себя

У `prove-it` есть `verify.sh`, и он прогоняет шлюз против настоящих git-репозиториев
во временном каталоге: проваленная проверка блокирует, пройденная разрешает, сессия
только на чтение не затрагивается, чистое дерево пропускается, обход работает.

```bash
./verify.sh
```

Было бы странно выпускать это иначе.
