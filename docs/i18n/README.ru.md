**Ваш агент не может завершить ход, пока репозиторий не докажет свою работоспособность.**

Кодовые агенты говорят "тесты проходят", не запустив их, и "исправлено", ни разу
не воспроизведя баг. Не из злого умысла: агент не отличает то, что он сделал, от
того, что он собирался сделать, поэтому он сообщает о намерении.

`prove-it` превращает *готово* в то, что агент обязан пройти, а не в то, что он
волен заявить. Положите `verify.sh` в корень репозитория. Когда агент пытается
остановиться, шлюз запускает его. Ненулевой код выхода - и ход не завершается.

![prove-it блокирует агента, который заявляет, что закончил](../../docs/demo.svg)

Примерно в половине случаев агент, у которого запросили доказательство, отвечает
"вы правы, это ещё не готово".

## Установка

Как плагин Claude Code:

```
/plugin marketplace add WhyNext/prove-it
/plugin install prove-it@whynext
```

Это вся установка. Плагин регистрирует два хука: один отмечает, что сессия
редактировала файлы, второй запирает ход.

Для любого другого агента, или если вы предпочитаете не ставить плагин,
клонируйте репозиторий и подключите те же два хука сами. Это обычный bash,
зависящий только от `bash`, `git` и `python3`:

```bash
git clone https://github.com/WhyNext/prove-it ~/.local/share/prove-it
```

Влейте [`hooks/settings.example.json`](../../hooks/settings.example.json) в свой
`.claude/settings.json` (для репозитория) или `~/.claude/settings.json` (везде).
Шлюз читает JSON-полезную нагрузку Stop hook со stdin и общается через код
выхода, поэтому всё, что умеет запускать скрипт в конце хода, может им управлять.

Затем напишите единственный файл, который важен:

```bash
cat > verify.sh <<'EOF'
#!/bin/bash
set -eu
cd "$(dirname "$0")"

npm test
npx tsc --noEmit
git diff --check

echo "verify.sh OK"
EOF
chmod +x verify.sh
```

Пока вы не написали этот файл, шлюз не делает вообще ничего.

## Ваши первые пять минут

Начните меньше, чем вам кажется. `verify.sh`, который запускает только
`git diff --check`, уже стоит иметь, и он пройдёт, что научит вас: шлюз молчит,
когда всё в порядке.

```bash
printf '#!/bin/bash\nset -eu\ncd "$(dirname "$0")"\ngit diff --check\n' > verify.sh
chmod +x verify.sh
./verify.sh                 # run it yourself first. Never ship a check you have not seen pass.
```

Теперь посмотрите, как он падает нарочно, чтобы вы знали, что шлюз настоящий:

```bash
sed -i.bak 's|git diff --check|git diff --check\nexit 1|' verify.sh && rm verify.sh.bak
```

Попросите агента отредактировать любой файл, а затем дайте ему закончить. Он
попытается завершить ход, шлюз запустит `verify.sh`, и ход будет заблокирован.
Уберите `exit 1`, и тот же агент пройдёт свободно.

Дальше добавляйте по одной настоящей проверке за раз: команду тестов, которую вы
и правда запускаете, потом проверку типов, потом гигиену диффа. Каждая
добавленная проверка - это предложение в вашем ответе на вопрос *что значит
доказано здесь*. Остановитесь, когда всё это занимает около минуты.

Ошибка, которой стоит избегать, - написать амбициозный `verify.sh` в первый же
день. Медленный или нестабильный шлюз обходят в течение недели, а обойдённый шлюз
хуже, чем никакого: он говорит вам, что проверка произошла, хотя её не было.

## Как он решает запускаться

Шлюз молчит по умолчанию. Он запускает `verify.sh` только когда истинно каждое
из следующего:

- сессия действительно редактировала файлы (сессии только на чтение нечего доказывать)
- исполняемый `verify.sh` существует в корне репозитория
- в рабочем дереве есть незакоммиченные изменения
- это точное состояние дерева ещё не проходило проверку

Последнее означает, что проходящее дерево проверяется один раз, а не при каждой
остановке. При провале агенту печатаются последние 20 строк вывода, чего обычно
достаточно, чтобы он исправил причину, не будучи об этом попрошенным.

Чтобы намеренно пройти мимо шлюза: `PROVE_IT_SKIP=1`. Чтобы выключить его
насовсем: удалите `verify.sh`. И то и другое - осознанное действие. Шлюз, который
никто не может убрать, - это шлюз, вокруг которого прокладывают обходные пути.

## Возможность отказаться - это фича

Самый тяжёлый режим отказа - не нестабильная проверка. Это агент, который не
может пройти `verify.sh` и тихо редактирует `verify.sh` вместо этого. Сообщение
об отказе шлюза говорит об этом прямым текстом, а спецификация делает это
заявленным нарушением. Всё равно следите за этим в своих диффах. Вот для чего
нужны доказательства в диффе.

## Соглашение `verify.sh`

Скрипт в `hooks/` намеренно мал. Настоящий артефакт - это соглашение, которое он
воплощает, записанное в **[SPEC.md](../../SPEC.md)**: репозиторий объявляет, как
он доказывает свою работоспособность, в известном месте, с известным контрактом,
и агент не вправе заявлять о завершении, пока это доказательство не пройдёт.

Плагин - это канал распространения, а не сама идея. Соглашение призвано пережить
любого отдельного агента, поэтому спецификация называет файл и код выхода, но
никогда не вендора.

Прочтите спецификацию, чтобы узнать о четырёх видах доказательств, против которых
`verify.sh` должен утверждать - вывод команды, дифф, воспроизведение,
перекрёстная проверка - и об уровнях соответствия.

**Одна честная оговорка сразу.** Этот инструмент обеспечивает ровно одно: что
`verify.sh` вернул ноль до того, как ход завершился. Значит ли этот ноль
*что-либо*, целиком зависит от проверок, которые вы написали. `verify.sh`,
содержащий только `exit 0`, пройдёт этот шлюз и не докажет ничего. Инструмент -
это Level 1. Доказательство - это Level 2, а Level 2 - это практика, а не фича.

## Рецепты

Отправные точки под каждый стек, в [`recipes/`](../../recipes/). Скопируйте один
в `verify.sh` и вырежьте то, что не применимо. Держите его в пределах минуты;
медленным проверкам место в CI.

| | |
|---|---|
| [`node.sh`](../../recipes/node.sh) | тесты, проверка типов, линт, гигиена диффа |
| [`python.sh`](../../recipes/python.sh) | pytest, ruff, mypy |
| [`go.sh`](../../recipes/go.sh) | go test, vet, проверка gofmt |
| [`flutter.sh`](../../recipes/flutter.sh) | analyze, test, проверка формата |

Тяжёлая часть внедрения этого - вовсе не подключение хука. Это ответ на вопрос
"что значит *доказано* в этом репозитории" в первый раз.

## Журнал

Установите `PROVE_IT_LEDGER=1`, и каждое пойманное ложное завершение дописывает
одну строку в `~/.prove-it/ledger.jsonl`:

```json
{"ts":"2026-07-09T04:12:33Z","claim":"All tests pass. Ready to merge.",
 "evidence_demanded":"verify.sh exit 0","actual":["3 failed, 41 passed"]}
```

Что было заявлено, что было потребовано, что было правдой. Только локальный диск,
никогда не передаётся, выключено, пока вы это не включите. Через месяц вы
перестаёте гадать о том, как ваш агент отказывает, и начинаете это читать.

## Этот репозиторий запирает сам себя

У `prove-it` есть `verify.sh`, и он запускает шлюз против настоящих git-репозиториев
во временной директории: провальная проверка блокирует, проходящая проверка
пропускает, сессия только на чтение остаётся нетронутой, чистое дерево
пропускается, обход работает.

```bash
./verify.sh
```

Было бы странно выпускать это иначе.

## Как внести вклад

Задачи и пул-реквесты приветствуются. Изменения самого соглашения относятся к
задаче, а не к пул-реквесту против эталонной реализации: соглашение - это
артефакт, скрипт - это сноска. См.
