版本 0.1（草案）。一个仓库声明它如何自证，而在那份证明通过之前，智能体不得声称完成。

这份文档就是契约。`hooks/` 里的脚本是它的一个实现，而且是有意做得很小的一个。在你假定这个工具会强制执行这里写的每一件事之前，先读第 5 节关于符合性等级的内容。

## 1. 问题

编程智能体会用这样的句子来结束回合：

- "测试通过。"测试从未运行过。
- "修好了这个 bug。"这个 bug 从未被复现过。
- "这次迁移是安全的。"什么都没在一个临时数据库上跑过。

这些并不是通常意义上的谎言。智能体无法把自己做过的事和自己打算做的事区分开，所以它的报告描述的是意图。这个失败是结构性的，靠提示词消除不了。提示词技巧还会随着每一代模型而过时，而对证据的要求处在模型之上的一层，能在升级中存活下来。

于是"完成"不再是智能体宣布的东西，而变成它必须通过的一次检查。

## 2. 约定

一个符合规范的仓库在其根目录有一个可执行文件 `verify.sh`。

```
your-repo/
  verify.sh      <- executable, exit 0 means "this tree is provably fine"
```

契约：

| | |
|---|---|
| 位置 | 仓库根目录 |
| 权限 | 可执行（`chmod +x`） |
| 调用方式 | 以仓库根目录为当前工作目录运行，不带参数 |
| 退出码 `0` | 验证通过 |
| 退出码非 `0` | 验证失败；stdout 和 stderr 说明原因 |
| 输出 | 人类可读；最后 20 行是智能体看到的内容 |
| 运行时长 | 一分钟以内；慢的检查该放到 CI 里 |
| 不存在 | 没有门禁。不存在是一个有效状态，而不是失败 |

`verify.sh` 回答一个问题：要让这里的一处改动可以被证明为安全、从而交还出去，什么必须为真？每个仓库对它的回答都不一样，这正是为什么这份约定指定的是文件本身，而不是它的内容。

选择退出只需一个动作：删除 `verify.sh`，或者把它砍成只剩 `exit 0`。这是刻意的。人们会绕开一个自己无法移除的门禁，而一个被绕开的门禁仍然会报告成功。

## 3. 四种证据

`verify.sh` 应当据以证据来断言，而不是据以信念。有四种证据有分量。一个有用的 `verify.sh` 至少覆盖其中一种，一个成熟的 `verify.sh` 会在它运行的各项检查中覆盖全部四种。

**命令输出。** 一个命令运行了，检查读取了它的退出码。不是"测试应该会通过"，而是测试运行器自己的裁决。

**Diff。** 这处改动正是所打算的，且仅此而已：没有调试语句，没有多余的文件，没有无关的格式变动。`git diff --check` 是底线。

**复现。** 对于一次 bug 修复，那个失败在改动之前被观察到，在改动之后消失了。一次从未被复现的修复，只是对哪一行出了错的一次猜测。

**交叉核对。** 第二个独立的来源表示同意。另一个模型，另一个工具，一个类型检查器对照一套测试。正是独立性让它有价值；两个共享同一假设的检查，确认的是那个假设，而不是代码。

这四个类别存在，是为了让"我验证过了"必须说出一个方法。一个说不出自己手里握着四种证据中哪一种的智能体，一种都没握着。

## 4. 实现必须做到什么

这份约定的一个实现就是一道门禁。要符合规范，它必须：

1. 在智能体的回合能够结束之前，从仓库根目录运行 `verify.sh`。
2. 在退出码非零时拦下这一回合，并把输出呈现出来。
3. 当门禁运行时 `verify.sh` 并不是一个可执行文件，而且在会话开始时它也不是一个可执行文件，什么都不做。
4. 当本次会话没有改动过那个仓库时，什么都不做。
5. 提供一个显式的、可用 grep 找到的绕过方式。一个静默的绕过会教人不信任门禁；一个留下审计痕迹的绕过则让它保持诚实。
6. 绝不在一次验证失败之后悄无声息地结束回合。一个出于任何原因停止拦截的实现，都必须在用户能看到的地方把这件事说出来。

第 4 点问的是什么变了，而不是谁改的。一个靠盯着智能体调用了哪些编辑工具来判断的实现，会漏掉一个被 `sed` 重写的文件、一个用 `git apply` 打上去的补丁、代码生成器的产物，以及一次提交。提交是智能体做的最寻常的事，而一个把干净的工作树当作没什么可证明的门禁，会把它本该抓住的那些回合恰恰放行掉。要拿仓库去和它在会话开始时的样子作比较。

第 3 点刻意使用这两个时刻。当前这个 stop 很重要，因为安装命令可以创建
`verify.sh`，并在同一个会话里把仓库武装起来。开始时的状态也很重要，因为会话
中途的删除或 `chmod -x` 应当被视为卸掉门禁，而不是诚实的退出。

第 6 点之所以存在，是因为一个能永远拦下去的门禁会把会话挂死，而每一个宿主最终都会强迫它让步。这没关系。有关系的是以一种和通过无法区分的方式让步。

它绝不能修改 `verify.sh`，而且它必须告诉智能体：为了越过门禁而削弱 `verify.sh` 是一种违规，而不是一次修复。这是实践中最可能出现的失败模式。一个过不了某项检查的智能体，一旦有机会，就会去改那项检查。

那种做法最粗暴的形式就是把检查移除掉。一个实现应当记录会话开始时 `verify.sh` 是否存在且可执行，并拒绝一个以它被删除或被卸掉而收场的回合。在两次会话之间删除这个文件是第 2 节里的那个退出方式，且必须继续有效。在它正要拦截的那次会话中途把它删掉，则不是一种退出方式，而这两者之间的区别，只有一个事先看过的实现才看得见。

## 5. 符合性等级

要对机器强制什么、人践行什么保持精确。这个区分比这份约定背后的雄心更重要。

**Level 1，门禁。** `verify.sh` 存在，而且有某个东西会在它失败时机械地拒绝让回合结束。`hooks/` 里的参考实现完整地强制这一点，每个仓库都应当从这里开始。"拒绝"是有额度的：它会把回合顶回去有限的若干次，然后带着一句警告让步，因为宿主不会让一个 hook 永远拦下去。

**Level 2，证据。** `verify.sh` 内部的检查覆盖了第 3 节里的四种证据。没有任何工具强制这一点，包括这一个。门禁验证的是你的 `verify.sh` 返回了零。那个零有没有意义，是一个关于你所写检查的主张，而一个只包含 `exit 0` 的 `verify.sh` 达到了 Level 1，却什么都没证明。

**Level 3，账本。** 每一次被抓到的虚假完成都被记录下来，好让这些失败模式变成数据而不是轶事。参考实现只在被显式启用时才写入它。

Level 1 是一个工具的属性。Level 2 是一个团队习惯的属性，任何声称能交付它的工具，交付的其实是 Level 1，然后指望没人去读源码。

## 6. 账本格式

启用时，每一次被抓到的虚假完成都会按每行一个 JSON 对象的方式追加：

```json
{
  "ts": "2026-07-09T04:12:33Z",
  "repo": "/home/you/src/api",
  "exit_code": 1,
  "claim": "All tests pass. Ready to merge.",
  "evidence_demanded": "verify.sh exit 0",
  "actual": ["FAIL src/auth.test.ts", "3 failed, 41 passed"]
}
```

`claim` 存放智能体在试图停止之前自己的最后一条消息。它是这条记录里最有用的字段，也是最敏感的字段，因为它可以包含任何对话文本。实现必须以受限权限把账本写入本地磁盘，并且绝不能传输它。

一行记录了三样东西：声称了什么，要求了什么，以及为真的是什么。

## 7. 非目标

这份约定不告诉你该检查什么，不运行你的 CI，不给你的代码打分，也不替代评审。它回答的是一个单一的问题：在智能体离开之前，这个仓库有没有完成自证。
